# Deferral Recognition Engine — Acceptance Criteria

Maps the master prompt's Phase 2.8 mandatory 29-item test list (plus Phase-1-derived items) to concrete scenarios, each with an ID (`DEFER-NNN`) for traceability in the completion report. Status column is filled in during Phase 3/4 execution.

| ID        | Category                         | Scenario                                                                                                                                                                                                                                                                                                | Status  |
| --------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| DEFER-001 | Functional                       | Create a valid Deferral schedule (201): header `ACTIVE`, N occurrence rows `SCHEDULED`, `Σ(amount_minor) = total_amount_minor`                                                                                                                                                                          | pending |
| DEFER-002 | Functional                       | Reject creation when occurrence amounts don't sum to the total (422)                                                                                                                                                                                                                                    | pending |
| DEFER-003 | Functional                       | Reject creation when `deferred_account_id = recognition_account_id` (422)                                                                                                                                                                                                                               | pending |
| DEFER-004 | Functional                       | Reject creation with an inactive/cross-tenant/cross-entity account (404/422, mirrors `revalidateLinesForPostingOrThrow` precedent)                                                                                                                                                                      | pending |
| DEFER-005 | Tenant isolation                 | Tenant B cannot list/read/cancel/process tenant A's schedules or occurrences                                                                                                                                                                                                                            | pending |
| DEFER-006 | Legal entity isolation           | Same, across legal entities within one tenant                                                                                                                                                                                                                                                           | pending |
| DEFER-007 | Occurrence generation            | N occurrences created with correct `sequence_number` (1..N), dates, amounts, all `SCHEDULED`                                                                                                                                                                                                            | pending |
| DEFER-008 | Due-date detection               | `process-due` selects only occurrences with `target_date <= cutoff` and status `SCHEDULED`                                                                                                                                                                                                              | pending |
| DEFER-009 | Future protection                | An occurrence not yet due is left untouched by `process-due`                                                                                                                                                                                                                                            | pending |
| DEFER-010 | One-to-one                       | One executed occurrence produces exactly one journal entry                                                                                                                                                                                                                                              | pending |
| DEFER-011 | Multiple occurrences             | A 12-occurrence schedule processed over multiple `process-due` calls reaches `COMPLETED` with 12 distinct journal entries                                                                                                                                                                               | pending |
| DEFER-012 | Amount preservation              | Each posted journal's line amounts exactly match its occurrence's `amount_minor`                                                                                                                                                                                                                        | pending |
| DEFER-013 | Journal balance                  | Every generated journal has equal total debit/credit (structural + `002_balance_invariant_trigger.sql` backstop)                                                                                                                                                                                        | pending |
| DEFER-014 | Period correctness               | Journal posts into the period actually covering `target_date`                                                                                                                                                                                                                                           | pending |
| DEFER-015 | Canonical numbering              | Generated journals receive sequential `JE-NNNNNN` numbers from the existing shared counter, no gaps/collisions under concurrency                                                                                                                                                                        | pending |
| DEFER-016 | Canonical posting path           | Generated journals are ordinary `journal_entries` rows created via `postSystemGeneratedEntry()` — no second posting engine, no direct `INSERT ... status='POSTED'` bypass                                                                                                                               | pending |
| DEFER-017 | Audit                            | Every lifecycle transition (create, cancel, execute, fail) writes the expected `audit_logs` row(s)                                                                                                                                                                                                      | pending |
| DEFER-018 | Provenance                       | `journal_entries` ← `deferral_recognitions.resultingJournalEntryId` ← `deferral_recognitions.scheduleId` ← `deferral_schedules` — full chain queryable in both directions                                                                                                                               | pending |
| DEFER-019 | Cancellation                     | Cancel a schedule with no executed occurrences → all `CANCELLED`; cancel a partially-executed schedule → only remaining `SCHEDULED` occurrences `CANCELLED`, executed ones untouched                                                                                                                    | pending |
| DEFER-020 | Amendment (Model B)              | No "amend" endpoint exists; amendment is demonstrated as cancel + create composed by the caller, per Phase 1.4                                                                                                                                                                                          | pending |
| DEFER-021 | Closed period                    | An occurrence due in a `CLOSED` period → `FAILED` with reason, never partially posts; remaining `SCHEDULED` occurrences of the same schedule continue to process independently on a later call                                                                                                          | pending |
| DEFER-022 | Retry (absence)                  | A `FAILED` occurrence is never automatically retried by any mechanism, per Phase 1.2 — no retry endpoint exists to test                                                                                                                                                                                 |
| DEFER-023 | Duplicate execution              | Two `process-due` calls in sequence never double-execute an already-terminal occurrence (mirrors `scheduled_reversals`' "running process-due twice is a no-op" test)                                                                                                                                    | pending |
| DEFER-024 | Concurrent execution             | 50-repetition real-PostgreSQL concurrent race — two simultaneous claim attempts on the same due occurrence resolve to exactly one `EXECUTED` outcome, no deadlock, ever (direct structural mirror of `scheduled-reversals-concurrency.e2e-spec.ts`)                                                     | pending |
| DEFER-025 | Terminal immutability            | A raw `UPDATE`/`DELETE` against an `EXECUTED`/`FAILED`/`CANCELLED` occurrence row, and against a `COMPLETED`/`CANCELLED` schedule row, is rejected at the trigger level — direct psql, bypassing the service layer (mirrors `scheduled-reversals.e2e-spec.ts`'s own "database-level enforcement" block) | pending |
| DEFER-026 | Authorization                    | `finance.viewer` can list/read but not create/cancel/process (403); `finance.admin` cannot create (403, mirrors `scheduled_reversals`' own RBAC test); `finance.poster` can do all mutating actions                                                                                                     | pending |
| DEFER-027 | Reporting/drill-down             | Active/upcoming/executed/failed/cancelled listings; schedule→journal and journal→schedule drill-down; derived remaining-balance calculation                                                                                                                                                             | pending |
| DEFER-028 | Regression — Journal Engine      | `journal-entries.e2e-spec.ts`, `journal-engine-db-constraints.e2e-spec.ts` remain 100% green, unmodified                                                                                                                                                                                                | pending |
| DEFER-029 | Regression — Scheduled Reversals | `scheduled-reversals.e2e-spec.ts`, `scheduled-reversals-concurrency.e2e-spec.ts` unmodified; the one pre-existing Category B failure (duplicate-schedule 409→500) persists unchanged, not newly broken or newly fixed                                                                                   | pending |
| DEFER-030 | Regression — Tax/VAT             | `tax-vat-phase-5/6`, `vat-position-*` suites remain 100% green, unmodified                                                                                                                                                                                                                              | pending |
| DEFER-031 | Regression — General Ledger      | `general-ledger.e2e-spec.ts`, `general-ledger-concurrency.e2e-spec.ts` remain 100% green, unmodified                                                                                                                                                                                                    | pending |
| DEFER-032 | Migration correctness            | `0025_deferral_recognition_engine.sql` applies cleanly on top of the verified baseline; RLS and constraint files apply cleanly; no existing migration/RLS/constraint file is modified                                                                                                                   | pending |
| DEFER-033 | Aggregate invariant backstop     | A direct-SQL attempt to insert/update occurrence rows such that `Σ(amount_minor) ≠ total_amount_minor` is rejected by the deferred constraint trigger at commit time, bypassing the service layer                                                                                                       | pending |
