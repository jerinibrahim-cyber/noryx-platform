## 1. Executive Summary

Supplier Payments and Customer Receipts can be posted today only if their allocations sum to exactly the header amount (`allocatedTotal === paymentAmountMinor`/`receiptAmountMinor`) and have at least one allocation line. Both restrictions are enforced by two explicit, intentionally-scoped guards inside each module's `post()` method — not by any accounting necessity, not by any schema constraint, and not by any business decision left open. They were deliberately imposed as an out-of-scope boundary as far back as the original AP-1a proposal and have been carried forward, verbatim, through every subsequent AP/AR work item's own "non-goals" section.

This proposal removes both guards and adds one new capability that does not exist today: applying an allocation to a bill or invoice _after_ the payment/receipt that pays for it has already posted. That capability is not a pure application-layer change — a database trigger (`008_supplier_payment_allocations_immutability_trigger.sql` / `012_customer_receipt_allocations_immutability_trigger.sql`) currently rejects **any** write to an allocation table once its parent document is POSTED, including `INSERT`. This proposal replaces both triggers with a narrowly-scoped successor that permits exactly one new operation — appending a brand-new allocation row to a still-live (not-yet-reversed) POSTED payment/receipt — while keeping every existing immutability guarantee (no `UPDATE`, no `DELETE`, ever) fully intact.

The GL posting itself requires no change: it is already header-amount-driven (proven in §3/§4 below) and will continue to post the full cash movement regardless of how much of it is allocated. The Balance Sheet and Cash Flow Statement are both allocation-agnostic today and require no change. Two real correctness gaps do exist and must be closed as part of this work, not deferred: (1) `getApReconciliation()`/`getArReconciliation()` today compare the sub-ledger's sum of open-bill balances against the raw GL control-account balance, and those two sides stay equal _only_ because every posted payment is fully allocated today — removing that invariant without adding an explicit "unapplied cash" reconciling term makes every reconciliation involving an on-account document silently report `reconciled: false` with no diagnosis; and (2) as-of/historical reporting filters allocation rows by the _parent payment's own business date_, which is safe today only because full allocation is required at post time (allocation and posting are contemporaneous) — once a later, separate allocation event becomes possible, that event needs its own business date to keep as-of reporting correct.

Recommendation: proceed. The change is a bounded, well-understood extension of an already-proven pattern (the existing `unsettleTarget()`/reversal machinery already handles an arbitrary number of allocations correctly with zero changes required), the accounting is provably correct without inventing any new GL account, and the two genuine gaps above have concrete, minimal, already-scoped fixes defined in this document.

**This revision (CTO Final Architecture Gate)** additionally resolves a fourth question the earlier drafts had left underspecified: whether `allocationDate` may be future-dated. It may not — `allocationDate` is capped at `todayUtc()` (§9.4 Rule 2), a direct consequence of this codebase's own established convention for genuinely future-effective financial events (`scheduled_reversals`, a deferred-execution design this work item deliberately does not replicate — §9.4). This closes a real potential inconsistency between live and as-of-today reporting, and — as a direct, provable consequence — makes "live" and "as-of-today" state identical at all times (§11.5), which this revision uses to define reconciliation's new `unappliedPaymentsMinor` term with exactly one formula rather than a separate live/as-of pair (§11.2). No new GL account, journal-entry type, or posting logic is introduced anywhere in this revision — every change remains confined to the sub-ledger/allocation layer already scoped in the paragraphs above.

## 2. Problem Definition

A supplier payment or customer receipt represents cash that has actually moved between the company's bank account and a counterparty. Today, the system requires that cash to be matched to open bills/invoices in full, in the same API call that posts it. Real-world AP/AR workflows routinely break that assumption: a supplier payment run may pay a round number the business chooses (not the exact sum of specific bills it has decided to match yet); a customer may remit an amount that does not line up with any single invoice; a company may want to record cash received today and decide which invoices it settles later, after reconciling with the customer. None of this is possible today — `post()` throws a `422` if the allocation total does not exactly equal the payment/receipt amount, and throws a `422` if there are no allocations at all.

The objective is to remove that restriction without weakening anything else the platform already guarantees: the double-entry GL posting, the reversal mechanism, RBAC, audit logging, tenant/legal-entity isolation, and document immutability once posted.

## 3. Existing Architecture

### 3.1 Module structure

Supplier Payments (`services/sphere-finance/src/accounts-payable/supplier-payments/`) and Customer Receipts (`services/sphere-finance/src/accounts-receivable/customer-receipts/`) are structural mirrors of each other, differing only in account polarity and entity names. Each module has: a controller (`@Controller("payments")` / `@Controller("receipts")`), a service, a set of DTOs, and a shared reliance on `services/sphere-finance/src/common/reversal/reversal.util.ts` for reversal-time settlement unwinding.

### 3.2 Lifecycle today

```
create()  → INSERT header (status DRAFT, default) + INSERT allocation rows (full array, from request)
update()  → DRAFT-only. Any header field patchable; allocations full-array-replaced (DELETE all, re-INSERT)
post()    → DRAFT → POSTED. Requires allocations.length >= 1 AND SUM(allocations) === header amount.
             Posts a 2-line journal entry for the FULL header amount. Settles each allocated bill/invoice
             (paidMinor += allocatedAmountMinor). Header, journal entry, and every settled bill/invoice
             get their own audit row.
reverse()  → POSTED only. Creates a new, debit/credit-swapped journal entry via the shared
             JournalEntriesService.completeReversalPosting(). Unwinds every row in before.allocations
             generically via unsettleTarget() (paidMinor -= allocatedAmountMinor per row). Works correctly
             for 0, 1, or N allocations with no special-casing (already proven; see §3.6).
```

There is **no existing capability to add an allocation to an already-POSTED payment/receipt.** Both controllers expose only `POST /`, `GET /`, `GET /:id`, `PATCH /:id`, `DELETE /:id`, `POST /:id/post`, `POST /:id/reverse`.

### 3.4 GL posting — header-amount-driven, confirmed

`supplier-payments.service.ts:511-528` (Step 12):

```ts
const journalLineValues = [
  { accountId: settings.apControlAccountId, debitMinor: before.paymentAmountMinor, creditMinor: 0, ... },
  { accountId: before.bankCashAccountId, debitMinor: 0, creditMinor: before.paymentAmountMinor, ... },
];
```

`customer-receipts.service.ts:535-547` (mirror, debit bank/cash, credit `arControlAccountId`, both lines for `before.receiptAmountMinor`). Both lines are always exactly two, always built from the **header field**, never from `before.allocations`. The journal entry's total is therefore always equal to the document's own amount, unconditionally, whether zero, some, or all of that amount is allocated to bills/invoices. This is the exact mechanism that makes on-account posting possible without any change to journal construction.

Bill/invoice settlement (`supplier-payments.service.ts:583-598`, Step 14) is a **separate** loop over `before.allocations` that increments `paidMinor`. With zero allocations this loop is a no-op; with N allocations it runs N times. No code path couples the journal-entry amount to the allocation total except the Step 9 guard being removed.

### 3.5 Immutability triggers — the real blocker for "apply allocation after posting"

`services/sphere-finance/drizzle/constraints/008_supplier_payment_allocations_immutability_trigger.sql` (customer-side mirror: `012_customer_receipt_allocations_immutability_trigger.sql`):

```sql
CREATE OR REPLACE FUNCTION prevent_posted_supplier_payment_allocation_mutation()
RETURNS TRIGGER AS $$
DECLARE
  target_payment_id uuid;
  parent_status supplier_payment_status;
BEGIN
  target_payment_id := COALESCE(NEW.payment_id, OLD.payment_id);
  SELECT status INTO parent_status FROM supplier_payments WHERE id = target_payment_id;
  IF parent_status = 'POSTED' THEN
    RAISE EXCEPTION 'supplier_payment_allocations is immutable once its parent supplier_payments is POSTED: % is not permitted (payment_id=%)',
      TG_OP, target_payment_id;
  END IF;
  IF TG_OP = 'DELETE' THEN RETURN OLD; END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

This trigger's own header comment states its intent explicitly: _"appending a new allocation to an already-posted payment would be just as much a rewrite of history as editing an existing one... `SupplierPaymentsService.post()` must never attempt to insert a new allocation row after flipping the parent payment to POSTED — it doesn't."_ This is a deliberate, DB-enforced design decision from the AP-1c work item, not an accident, and it is precisely the behavior this proposal must change (narrowly — see §15/§16). It is the single most consequential fact this investigation surfaced beyond the two `post()` guards: **this feature is not purely an application-layer change.**

Also relevant: `supplier_payment_allocations` has a `unique(paymentId, billId)` constraint — at most one allocation row per bill per payment. Its own schema comment states the intended semantics: _"an edit to an existing allocation changes this row's amount rather than adding a second row for the same pair."_ That semantics was correct when allocations were only ever edited pre-POST (via full-array-replace). It is **not** compatible with an append-only, post-POST allocation history, and must be relaxed (§15).

### 3.6 Reversal — proven safe for N allocations already

`unsettleTarget()`, `services/sphere-finance/src/common/reversal/reversal.util.ts:89-129`:

```ts
export async function unsettleTarget<T extends UnsettleableTargetTable>(
  tx: TxClient,
  table: T,
  target: UnsettleableTargetRow,
  unapplyAmountMinor: number,
): Promise<UnsettleableTargetRow> {
  const newPaidMinor = target.paidMinor - unapplyAmountMinor;
  if (newPaidMinor < 0) {
    throw new Error(
      `Internal invariant violation: ... would produce a negative paidMinor ...`,
    );
  }
  const newPaymentStatus =
    newPaidMinor === 0
      ? "UNPAID"
      : newPaidMinor === target.totalMinor
        ? "PAID"
        : "PARTIALLY_PAID";
  const rows = await tx
    .update(table)
    .set({ paidMinor: newPaidMinor, paymentStatus: newPaymentStatus })
    .where(eq(table.id, target.id))
    .returning();
  return rows[0];
}
```

`supplier-payments.service.ts`'s `reverse()` calls this inside `for (const allocation of before.allocations)`, with `before` freshly re-loaded (under `FOR UPDATE`) at the start of `reverse()` itself. This loop is already generic over 0, 1, or N allocations (the `billIds.length ? ...lockedBills... : []` guard at lines 682-693 already exists specifically to make the 0-allocation case safe). **Consequence for this proposal: `reverse()` requires zero code changes.** Whatever allocation rows exist on a payment/receipt at the moment it is reversed — whether written at create-time, added later via the new apply-allocation endpoint, or a mix — are unwound correctly, because `reverse()` always re-reads the live allocation set rather than assuming it was fixed at post time.

The generic reversal engine itself, `JournalEntriesService.completeReversalPosting()` (`journal-entries.service.ts:545-677`), creates a brand-new journal entry with every line's debit/credit swapped (not negated), on the identical account set, and never mutates or deletes the original entry or its lines — confirmed by direct reading, not by name alone. Double-reversal is centrally blocked in `lockAndValidateOriginalForReversal()` (`journal-entries.service.ts:501-527`), which every document type's `reverse()` calls before doing anything else.

### 3.7 Reporting

**Balance Sheet** (`financial-statements.service.ts`, `fetchTypeBalancesAsOf`): reads raw `journal_lines`/`journal_entries` grouped by `chart_of_accounts.type`. It never references `supplierBills`, `customerInvoices`, `apControlAccountId`, or `arControlAccountId` by name — it is allocation-agnostic by construction and requires **zero code change**.

**Cash Flow Statement** (`financial-statements.service.ts`, the `entry_flags` CTE and `contribution()`): an entry is "reconciling" (counted in Operating/Investing/Financing) iff at least one of its lines touches a configured cash account or a REVENUE/EXPENSE account. A payment/receipt's journal entry always has one line on the bank/cash account (§3.4), so it is always classified as reconciling, regardless of allocation state. This requires **zero code change**.

**AP/AR ageing** (`ap-reports.service.ts`/`ar-reports.service.ts`): computed purely from `supplier_bills.totalMinor - paidMinor` / `customer_invoices.totalMinor - paidMinor`. Neither `supplier_payments` nor `customer_receipts` is joined into the ageing query at all. An unallocated payment is therefore invisible to ageing — which is accounting-correct (§6) — but on-account cash is also currently invisible to the _business user_, with no line anywhere showing it exists. This proposal adds visibility (§11) without changing the ageing calculation itself.

**Reconciliation** (`getApReconciliation()`/`getArReconciliation()`, quoted in full in §11.2): compares `subLedgerTotalOutstandingMinor` (sum of open-bill balances) against `glApControlAccountBalanceMinor` (raw GL control-account balance from `journal_lines`). These two sides are equal **today only because every posted payment is fully allocated** — an implicit invariant enforced entirely by the Step 3/Step 9 guards being removed, with no explicit reconciling term anywhere in the formula. This is a real correctness gap this proposal must close (§11.2).

**As-of/historical reporting** (`asOfTotals()` in both report services, complete text re-read in full for this revision — not excerpted): the bill/invoice-side subquery is already reversal-aware (`LEFT JOIN journal_entries je ... LEFT JOIN journal_entries rev_je ON rev_je.id = je.reversed_by_journal_entry_id ... AND (je.reversed_by_journal_entry_id IS NULL OR rev_je.transaction_date > cutoffDate)`, AP: lines 839-849; AR: lines 886-895 — unchanged, not touched by this proposal). The **allocation-side subquery**, by contrast, today has neither an allocation-event-level date (only `sp.payment_date <= cutoff`/`sp.receipt_date <= cutoff`, the parent document's own date) nor any join to `journal_entries` at all (AP: lines 852-867; AR: lines 899-914) — confirmed by full re-read, not excerpt. This proposal closes **both** gaps in the allocation-side subquery together, as a single, indivisible change: the new `allocation_date` column (§15) replaces the parent-date predicate, and a new reversal-timing join — structurally identical to the bill-side join already in production two lines above it in the same method — is added alongside it. The exact, complete resolution, including why these two gaps cannot be closed independently of each other, is given in §11.4.

This is a revision from this proposal's own earlier draft, which had incorrectly treated the allocation-side reversal-timing gap as the _same_, pre-existing, out-of-scope limitation the method's doc comment (AP: lines 776-786; AR: lines 874-880) discloses. On full re-read: that doc comment's disclosed limitation is real, but it describes exactly this gap — it was never actually "a different, pre-existing issue"; it is precisely the allocation-side reversal-timing gap this work item must close, because until now (zero allocation and posting always contemporaneous) it had no observable consequence, and this work item is what first makes it observable. Closing it is therefore in scope, not adjacent to scope. §11.4 gives the complete, re-verified resolution.

### 3.8 Audit, RBAC, concurrency — existing conventions

Audit: no `AuditLogService` wrapper and no schema-enforced action vocabulary — `audit_logs.action` is a plain `varchar(255)`. Twelve distinct free-form values are in active use today: `CREATE, UPDATE, DELETE, POST, REVERSE, ARCHIVE, DEACTIVATE, REACTIVATE, CANCEL, EXECUTE, FAIL, CLOSE`. `UPDATE` is already the convention for "a mutation to an entity's persisted state" broadly — including the existing full-array allocation replace inside `update()`.

RBAC: exactly three roles exist anywhere in the Finance service — `finance.viewer`, `finance.poster`, `finance.admin` (confirmed by grep over all 150 `@Roles(...)` call sites). `create/update/post/reverse` all require `finance.poster` today.

Concurrency: no optimistic-concurrency/version column exists anywhere in the schema. All concurrency control is `SELECT ... FOR UPDATE` pessimistic row locking, taken in a fixed order (document header row, then every target bill/invoice row in ascending-`id` order) to avoid deadlocks across concurrently-posting/reversing documents. `withTenant()` opens every mutating call in a single `READ COMMITTED`, read-write transaction (no explicit `txConfig`), covering the entire method body with no intermediate commit.

## 5. Proposed Architecture

Three changes, each independently necessary and jointly sufficient:

1. **Posting-time relaxation.** In both `post()` methods: remove the "at least 1 allocation" guard; change the exact-equality allocation-sum guard to an upper-bound guard (`allocatedTotal > headerAmount` is still rejected; `allocatedTotal < headerAmount`, including `0`, is now accepted).
2. **A new allocation-application capability**, exposed as one new endpoint per module (`POST /payments/:id/allocations`, `POST /receipts/:id/allocations`), permitting a POSTED, not-yet-reversed document to have a new allocation row appended against any open bill/invoice belonging to the same supplier/customer, up to its own remaining unapplied balance.
3. **Reporting/schema support** for the above: an explicit "unapplied cash" reconciling term in `getApReconciliation()`/`getArReconciliation()`; a visible "unapplied" balance field on `getSupplierBalance()`/`getCustomerBalance()`; a new `allocationDate` column on both allocation tables so a later allocation event carries its own business date for as-of correctness; a relaxed `unique(paymentId, billId)` constraint (now a plain index) so a bill/invoice can receive more than one allocation event from the same payment/receipt over time; and a new, narrower version of the immutability trigger that permits exactly one new operation (`INSERT` on a POSTED-but-not-reversed parent) while continuing to forbid `UPDATE`/`DELETE` unconditionally, at every parent status.

No new GL account, account type, or settings field is introduced (proven in §6). No new document type is introduced — this is an extension of the existing Supplier Payment / Customer Receipt document types, not a new one.

## 6. Accounting Model

### 6.1 Why no new "unapplied cash" GL account is needed

The AP/AR control account's role in the ledger is to represent the net amount currently owed to/by a counterparty in aggregate. Per-bill/invoice detail (ageing, dunning, matching) is sub-ledger information layered on top of that aggregate figure; it is an operational view, not itself a GL concept. Cash that has left the company's bank account for a supplier — or arrived from a customer — has genuinely changed what is owed to/by that counterparty in aggregate the instant it posts, whether or not it has yet been matched to a specific bill/invoice. Debiting the AP control account (crediting the AR control account) for the full cash amount, unconditionally, is the correct double-entry treatment for that fact, independent of matching state. This proposal does not invent that treatment — it is already exactly what `post()` does today (§3.4); this proposal only removes the requirement that matching happen atomically with posting.

A distinct "unapplied cash"/"customer advances" account would only be needed if the business wanted it to appear as its own line item on the Balance Sheet, separate from "Accounts Payable"/"Accounts Receivable" — a presentation decision, not an accounting-correctness requirement. Nothing in the CTO's instruction, the repository, or any existing proposal signals that such a distinct presentation is required. It is recorded as a Future Extension (§16), not a requirement of this work item. Confirmed by exhaustive search: no `accountTypeEnum` value, `ap_settings`/`ar_settings` field, or schema comment anywhere in the repository references such a concept (§3.7 investigation, Finding 11).

### 6.2 Formal invariants

Notation: for a payment `p`, `appliedMinor(p) = SUM(allocatedAmountMinor)` over every row in `supplier_payment_allocations` where `paymentId = p.id` (all rows, all time — rows are never updated or deleted once inserted, so this sum is always the true, current, cumulative applied amount). `unappliedMinor(p) = p.paymentAmountMinor - appliedMinor(p)`.

1. **Journal amount == header amount, always.** `debitMinor = creditMinor = p.paymentAmountMinor` on both lines of `p`'s journal entry, unconditionally (§3.4). Unaffected by this proposal — already true, remains true.
2. **Total allocation never exceeds the header amount.** `appliedMinor(p) <= p.paymentAmountMinor` at all times. Was previously an equality; becomes an inequality. Enforced at both `post()` time (initial allocations) and at every subsequent apply-allocation call (§9).
3. **Allocation changes never alter historical journal posting.** Unaffected — no code path from any allocation write ever touches `journal_entries`/`journal_lines` of an already-posted entry. Continues to hold.
4. **Allocation affects settlement state, not the original cash movement.** `paidMinor` on the target bill/invoice is the only thing an allocation event changes on the target side; `p`'s own journal entry, once posted, is never revisited. Continues to hold, and is the mechanism this whole proposal depends on.
5. **Reversal reverses the accounting effect exactly once.** `lockAndValidateOriginalForReversal()`'s `reversedByJournalEntryId`/`reversalOfJournalEntryId` guard (§3.6) makes a double-reversal impossible for any document, on-account or not. Unaffected.
6. **Reversal never creates a replacement posting nor deletes history.** `completeReversalPosting()` only ever inserts a new entry and sets one link column on the original (§3.6). Unaffected.
7. **Unapplied amount is deterministically derivable.** `unappliedMinor(p) = p.paymentAmountMinor - appliedMinor(p)`, computable at any instant from persisted data with no ambiguity. New invariant, established by this proposal, and is exactly the quantity exposed in §11.
8. **`paidMinor` on a bill/invoice remains internally consistent** with the CHECK constraint `0 <= paidMinor <= totalMinor` already present on both tables (`supplier_bills_paid_minor_within_total`, `customer_invoices_paid_minor_within_total`). Every write path to `paidMinor` (post-time settlement, apply-time settlement, reversal-time unsettlement) is required by this proposal to stay within that bound; each is proven to do so in §9/§10.
9. **Current-mode reporting reconciles.** True today; requires the explicit "unapplied cash" reconciling term defined in §11.2 to remain true once on-account documents exist.
10. **As-of reporting respects event timing.** Requires the new `allocationDate` column defined in §15 to remain true once a later, independent allocation event can exist.
11. **Cross-entity allocation is impossible.** Enforced today by `validateAllocationsShapeOrThrow()`'s tenant/legal-entity/supplier(customer) scoping on every bill/invoice id supplied (§3.3's neighboring code); the new apply-allocation endpoint reuses this exact check (§9.1) — continues to hold.
12. **Concurrent operations preserve every invariant above.** Proven in §14 via the existing lock-ordering convention, extended (not replaced) by this proposal.

## 7. State Model

No new status value is introduced on either the payment/receipt or the bill/invoice. `supplierPaymentStatusEnum`/`customerReceiptStatusEnum` remain exactly `DRAFT | POSTED` (confirmed — no `REVERSED` value exists; a reversed document stays `POSTED` with reversal metadata carried on its journal entry, the existing pattern for every reversible document type). `billPaymentStatusEnum`/`invoicePaymentStatusEnum` remain exactly `UNPAID | PARTIALLY_PAID | PAID`, recomputed from `paidMinor` by the exact same three-way `newPaidMinor === 0 ? "UNPAID" : newPaidMinor === totalMinor ? "PAID" : "PARTIALLY_PAID"` logic already used by both `post()` and `unsettleTarget()` (§3.6) — the new apply-allocation path reuses this identical logic, not a new variant of it.

A payment/receipt's own "how much of me is applied" state is **not** stored as a denormalized column on the header (no new `unappliedMinor` column is added to `supplier_payments`/`customer_receipts` — see §15 for why this is a deliberate choice, not an omission). It is always derived at read time from `SUM(allocatedAmountMinor)` over its allocation rows, per Invariant 7 above. This keeps the header itself append-only-safe under the relaxed trigger (§3.5) — no header column write is needed when a later allocation event occurs.

```
DRAFT ──create()──> DRAFT ──update()──> DRAFT ──post()──> POSTED(applied = initial allocations, possibly 0)
                                                              │
                                                              ├── applyAllocation() ──> POSTED(applied += new allocation)
                                                              │        (repeatable, any number of times,
                                                              │         until applied == paymentAmountMinor
                                                              │         or the document is reversed)
                                                              │
                                                              └── reverse() ──> POSTED, journalEntry.reversedByJournalEntryId set
                                                                                 (applyAllocation() now permanently blocked,
                                                                                  §9.3; every currently-applied allocation
                                                                                  unwound by the single reverse() call, §10)
```

## 9. Allocation Lifecycle

### 9.1 `applyAllocation()` — exact step sequence (mirrors `post()`'s own step numbering style)

```
Step 1  — withTenant(tenantId, async (tx) => { ... })
Step 2  — Lock the payment header: findByIdInTx(tx, tenantId, legalEntityId, id, { forUpdate: true }).
          404 if not found.
Step 3  — if (before.status !== "POSTED") throw UnprocessableEntityException(
              "Only a posted supplier payment can receive a new allocation.");
Step 4  — if (!before.journalEntryId) throw UnprocessableEntityException(
              "This supplier payment has no posted journal entry.");    // structurally unreachable
              // once Step 3 passes, kept for parity with reverse()'s own defensive check
Step 5  — Load before.journalEntryId's own reversedByJournalEntryId.
          if (it is not null) throw ConflictException(
              "This supplier payment has already been reversed and cannot receive further allocations.");
Step 6  — currentlyAppliedMinor = SUM(allocatedAmountMinor) over ALL existing rows in
          supplier_payment_allocations where paymentId = id (this is appliedMinor(p) from §6.2).
Step 7  — validateAllocationsShapeOrThrow(tx, tenantId, legalEntityId, before.supplierId, dto.allocations)
          — the EXACT existing method (§3.3's neighbor), reused unmodified: rejects duplicate billIds
          within this request, and rejects any billId not belonging to this payment's own supplier in
          this legal entity.
Step 8  — requestedTotal = SUM(dto.allocations[*].allocatedAmountMinor).
          if (currentlyAppliedMinor + requestedTotal > before.paymentAmountMinor)
            throw UnprocessableEntityException(
              `Applying ${requestedTotal} would bring this payment's total applied amount to
               ${currentlyAppliedMinor + requestedTotal}, exceeding its amount of
               ${before.paymentAmountMinor}.`);
Step 9  — effectiveAllocationDate = dto.allocationDate ?? todayUtc().
          if (effectiveAllocationDate > todayUtc())
            throw UnprocessableEntityException(
              `Allocation date ${effectiveAllocationDate} cannot be later than today
               (${todayUtc()}) — this endpoint does not support a future-effective allocation.`);
          — CTO Architecture Gate, Final Revision, Option A (§9.4 Rule 2): a definitive ceiling,
          replacing this proposal's earlier draft position that a future-dated OPEN period was
          acceptable. See §9.4 Rule 2 for the full repository-evidence justification (the
          `scheduled_reversals` precedent).
          if (effectiveAllocationDate < before.paymentDate)
            throw UnprocessableEntityException(
              `Allocation date ${effectiveAllocationDate} cannot be earlier than this payment's own
               payment date ${before.paymentDate}.`);
          — a new, explicitly-invented rule (no prior convention in this codebase compares one
          document's date to a related document's date; see §9.4 Rule 1 for the full reasoning).
Step 10 — resolveAndLockOpenPeriod(tx, tenantId, legalEntityId, effectiveAllocationDate)  — the SAME
          shared helper/convention post()/reverse() already use (journal-entries.service.ts's
          resolveAndLockOpenPeriod / resolvePeriodForDate, reused via
          common/reversal/reversal.util.ts's resolveOpenPeriodOrThrow), called against the
          ALLOCATION EVENT'S OWN effectiveAllocationDate — not before.paymentDate. NOT_FOUND or
          CLOSED → UnprocessableEntityException, exact existing message pattern with "allocation
          date" substituted (see §9.4 Rules 3-4). Because Step 9 already bounds
          effectiveAllocationDate to the closed range [before.paymentDate, todayUtc()], this
          step's practical effect is to reject a CLOSED historical period somewhere in that
          range — the future-period question Step 9 previously deferred to this step no longer
          arises, since a future date never reaches Step 10 at all.
Step 11 — Lock every targeted bill, fixed ascending-id order (identical pattern to post() Step 7 / reverse()):
              billIds = dto.allocations.map(a => a.billId)
              lockedBills = billIds.length
                ? SELECT ... FROM supplier_bills WHERE id IN (billIds) AND tenantId = ... AND legalEntityId = ...
                    ORDER BY id ASC FOR UPDATE
                : []
Step 12 — For each targeted bill, re-validate under lock (identical checks to post() Step 8):
              exists in scope; status === "POSTED"; bill.supplierId === before.supplierId;
              allocation.allocatedAmountMinor <= (bill.totalMinor - bill.paidMinor)  // else 422
Step 13 — INSERT one new row per dto.allocations[*] into the allocation table, each with
          allocationDate = effectiveAllocationDate (already validated as >= before.paymentDate and
          inside the resolved open period by Steps 9-10). No existing row is ever read, merged into,
          or updated — this is an append-only insert, matching the relaxed trigger's only permitted
          new operation (§15).
Step 14 — For each newly-inserted allocation, settle its target bill exactly as post() Step 14 does:
              newPaidMinor = bill.paidMinor + allocation.allocatedAmountMinor
              newPaymentStatus = newPaidMinor === 0 ? "UNPAID" : newPaidMinor === bill.totalMinor ? "PAID" : "PARTIALLY_PAID"
              UPDATE supplier_bills SET paidMinor = newPaidMinor, paymentStatus = newPaymentStatus WHERE id = bill.id
              // same "never set updated_at" caveat as post() Step 14, for the same immutability-trigger reason
Step 15 — Audit: one UPDATE row on entityType "supplier_payment" (beforeState = the payment WITH its
          allocation list as it was before this call; afterState = the payment WITH its full, current,
          cumulative allocation list after this call — same convention post()/update() already use), plus
          one UPDATE row per settled bill on entityType "supplier_bill" (before/after paidMinor+paymentStatus,
          identical shape to post()'s own per-bill audit rows).
Step 16 — Return the payment with its full current allocation list (findByIdInTx, no lock needed for the
          return read).
```

Customer Receipts mirror: `receiptAmountMinor`/`invoiceId`/`customerInvoices`/`entityType: "customer_receipt"`/`"customer_invoice"`, otherwise identical step-for-step.

### 9.2 Why this does not reintroduce the removed post-time guards in disguise

Step 8's inequality (`currentlyAppliedMinor + requestedTotal > before.paymentAmountMinor` → reject) is the incremental, always-enforced form of Invariant 2 (§6.2) — it is not a restatement of the old exact-equality Step 9 guard, which required the total to equal the header amount before the document could even become POSTED. Under this proposal a payment may remain POSTED forever at `appliedMinor(p) = 0` — nothing anywhere requires it to ever reach full application.

### 9.3 Why a reversed document cannot receive a new allocation (Step 5)

Once `reverse()` has run, the payment's cash movement has been accounting-reversed — its net GL effect is zero. Allowing a further allocation afterward would settle a bill/invoice using cash that the ledger says was returned, silently reintroducing an inconsistency between the sub-ledger (`paidMinor`) and the GL (net-zero journal effect). This is blocked at the application layer (Step 5) for a clean `409`, and independently at the database layer by the relaxed trigger (§15) as defense-in-depth — the same two-layer pattern (`ConflictException` + trigger) the codebase already uses for every other immutability guarantee.

### 9.4 Allocation Date & Accounting Period Semantics — definitive rules

This section resolves, precisely and without ambiguity, every question about the new `allocationDate` field's relationship to accounting periods and to the parent document's own date. Each rule states the repository convention it reuses, or states explicitly that no convention exists and a new rule is being defined (per the investigation's own findings — full method/schema re-reads, not excerpts, confirmed the following are the only relevant precedents in this codebase).

**Rule 1 — `allocationDate` may not be earlier than the parent document's own `paymentDate`/`receiptDate`.** No existing convention in this codebase validates one document's date against a related document's date (confirmed by exhaustive search: the only two cross-field date validators found, `is-after-date`/`is-same-or-after-date`, are used exclusively for a single row's own two fields — e.g. `endDate` after `startDate` on an accounting period — or a report query's `dateFrom`/`dateTo` range; never for two different related documents). This is therefore a **new rule, explicitly invented for this feature, not reused** — stated plainly rather than disguised as an existing convention. Justification: the cash represented by a payment/receipt did not exist, in the ledger, before that payment/receipt's own `paymentDate`/`receiptDate` (that is the date its journal entry posted, per §3.4). An allocation dated earlier than that would let a bill's/invoice's as-of history show it "settled" by cash that, as of that earlier date, had not yet moved — an accounting-sequence violation the existing accounting model has no other way to prevent (no schema-level ordering constraint links the two tables' dates). Enforced at the application layer only (Step 9, §9.1) — not a new DB constraint, consistent with every other business-rule check in `post()`/`applyAllocation()` (Steps 8, 10, 12) being application-layer, with only the universal invariants (positive amounts, `paidMinor` bounds) enforced as DB `CHECK` constraints.

**Rule 2 (REVISED — CTO Architecture Gate, Final Revision, Option A) — `allocationDate` may not be later than `todayUtc()`; a future-dated allocation is rejected outright.** This reverses this proposal's earlier draft position (which accepted any date inside an `OPEN` period, including a future one) after the CTO's gate correctly identified that accepting a future `allocationDate` while `applyAllocation()` immediately mutates live `paidMinor` produces exactly the inconsistent state the gate's example describes: a live bill shown fully settled today, while an as-of-today report shows it unsettled, for a "settlement" that has not — by the payment's own stated allocation date — happened yet. That inconsistency is real and this proposal does not attempt to paper over it with narrower reporting logic. Direct repository evidence resolves which of the CTO's two options applies: this codebase already has an established mechanism for a genuinely future-effective financial event — `scheduled_reversals` (`schema.ts:2795-2830`, `scheduled-reversals.service.ts`) — and it is deliberately **not** a live-state mutation with a future date attached. A scheduled reversal is created in a `SCHEDULED` status that has **zero effect on any live balance until it executes**; a background claiming job (`scheduled-reversals.service.ts:288-289`, `WHERE status = 'SCHEDULED' AND target_date <= cutoff`) locates rows whose `targetDate` has actually arrived and only _then_ invokes the ordinary, unmodified reversal-posting path. Nothing is ever inserted, updated, or read as "already applied" before its effective date arrives. This is the only precedent in the entire repository for "an event dated in the future," and it is built as a deferred-execution subsystem — a status lifecycle, a claiming/execution job, idempotent re-claim semantics — not as an immediate write gated by a date comparison. `applyAllocation()`, as scoped by this proposal, is a synchronous, single-transaction, immediate-effect write; it has no scheduling, claiming, or execution-job mechanism, and building one would mean inventing a second deferred-execution subsystem parallel to `scheduled_reversals` — a substantial, unapproved expansion of this work item's scope (subledger allocation capability, not a new scheduling engine), and exactly the overdesign the CTO's own gate instruction warns against. Per the CTO's explicit fallback instruction ("if these semantics cannot be made clean and internally consistent with the existing Sphere model, choose Option A"), **Option A is selected**: `allocationDate` is capped at `todayUtc()`, full stop. A business need for genuinely future-effective on-account allocations, should one emerge, is a distinct future work item scoped around `scheduled_reversals`'s own established pattern — not a variant grafted onto this one (recorded as a Future Extension, §16).

**Rule 3 — `allocationDate` is validated against an OPEN accounting period covering that date; a CLOSED period is rejected.** Directly reused, not invented: `resolveAndLockOpenPeriod()`/`resolvePeriodForDate()` (`journal-entries.service.ts`) is the single existing mechanism, already called at exactly 15 sites across every one of the 8 reversible document types' `post()`/`reverse()` methods, always rejecting a `CLOSED`-period date with `UnprocessableEntityException` (exact message: `` `Accounting period "${period.code}" covering ${date} is closed.` ``, field name substituted per call site's own convention — here, "allocation date"). `applyAllocation()` reuses this helper unmodified, called with `effectiveAllocationDate`. Because Rule 2 already caps `effectiveAllocationDate` at `todayUtc()`, and the period covering "today" must be `OPEN` in ordinary operation (nothing in this codebase can post anything, of any kind, on a day whose own period is closed), this rule's practical effect narrows to rejecting a `CLOSED` period strictly between `before.paymentDate` and today — the "future OPEN period" question this proposal's earlier draft debated no longer arises, because a future date is rejected one step earlier, at Rule 2, before period resolution is ever reached.

**Rule 4 — a date with no covering `accounting_periods` row at all is rejected identically to a closed period, with `NOT_FOUND`'s own message.** Reused precisely: this codebase's resolver does not distinguish "no period exists yet" from "no period exists" — both produce the identical `UnprocessableEntityException` (`` `No accounting period covers transaction date ${date} for this legal entity.` ``, field name substituted). `applyAllocation()` inherits this behavior unmodified via the same shared helper. Since Rule 2 forecloses any date later than today, this rule's realistic trigger is a genuine historical gap in period coverage (e.g. a legal entity onboarded partway through a fiscal year, with no period record for a date before onboarding), not a not-yet-created future period.

**Rule 5 — when `allocationDate` is omitted from the request, it defaults to the server's current UTC date (`todayUtc()`), not the parent document's own `paymentDate`/`receiptDate`.** Reused, not invented: this is the exact precedent `reverse()` itself already establishes for its own optional, defaultable event-date field — `const transactionDate = dto.transactionDate ?? new Date().toISOString().slice(0, 10);` (`customer-receipts.service.ts:748-749`, byte-identical in every other `reverse()`). `applyAllocation()` is structurally the same case — a later, separately-dated action against an already-posted document with an optional date field — and reuses the identical default. This default is, by construction, never later than `todayUtc()` itself, so it can never violate Rule 2.

**Rule 6 — validation is performed against the allocation event's own period, never the parent document's original period.** Reused, not invented: `reverse()` never re-validates the _original_ posting's period; it resolves and locks the period covering its _own_ (possibly defaulted) `transactionDate`, entirely independent of whatever period the original entry posted into. `applyAllocation()` is the direct structural analogue and follows the identical rule — Step 10 (§9.1) resolves the period covering `effectiveAllocationDate`, never `before.paymentDate`'s period.

**Rule 7 — period-open enforcement applies to the allocation event even though it inserts no `journal_entries` row.** This is the one point in this section where the investigation found **no existing precedent either way** — every one of the 15 existing period-enforcement call sites sits inside a method that also inserts or reverses a `journal_entries` row; `paidMinor` has never before been mutated by a write that does not also touch `journal_entries` in the same transaction, so this is a genuine first fork in the convention, not a reuse. The decision, stated explicitly rather than left ambiguous: **enforce it.** Reasoning: the existing convention's own stated purpose (see the Step 15 audit-comment pattern, "audit all financially significant state changes," and the very existence of a `periodId` lock on every posted document) is about controlling which business dates a financially significant event may land on — and `applyAllocation()` mutates `paidMinor`, a financially significant sub-ledger state, exactly as `post()` Step 14 and `reverse()`'s `unsettleTarget()` already do, both of which are always period-gated today. Treating "inserts a `journal_entries` row" as the operative trigger, rather than "mutates a financially significant balance," would be reading a mechanical accident of every prior feature (period gating and journal-entry creation always having been co-located, by coincidence, until now) as an intentional design boundary it was never actually written to express.

**Summary — no ambiguity remains:** `effectiveAllocationDate = dto.allocationDate ?? todayUtc()`; rejected with `422` if earlier than `before.paymentDate`/`before.receiptDate` (Rule 1); rejected with `422` if later than `todayUtc()` (Rule 2, revised — no future-effective allocation, by direct repository evidence); rejected with `422` if its own covering period is `CLOSED` or does not exist (Rules 3, 4); validated against its own period, never the parent's (Rule 6); enforced even though no journal entry is created (Rule 7, a new but reasoned fork). Because `effectiveAllocationDate` is now bounded on both ends — never before `paymentDate`, never after `todayUtc()` — "live" (current) state and "as-of-today" state are now provably identical at all times (§11.5): there is no longer any way for a `paidMinor` mutation to exist that an as-of-today report cannot also see, which is precisely the class of inconsistency the CTO's gate flagged. All seven rules are implemented as Steps 9-10 of §9.1's step sequence — none is deferred to implementation-time judgment.

## 10. Reversal Lifecycle

**No code change to `reverse()` in either module.** Traced precisely against the CTO's own worked example:

```
1. Supplier Payment = 1,000, posted with zero allocation.        → appliedMinor = 0
2. Later, allocated 600 to Bill A via applyAllocation().         → appliedMinor = 600; Bill A.paidMinor += 600
3. Later, allocated 400 to Bill B via applyAllocation().         → appliedMinor = 1000; Bill B.paidMinor += 400
4. Payment is reversed.
```

At step 4, `reverse()` (unchanged code) executes exactly as it does today for any fully-allocated payment: it re-loads `before` under `FOR UPDATE`, which now reflects **both** allocation rows (from steps 2 and 3 — `before.allocations` is not a snapshot taken at post time; it is read fresh, right now, by this call). It locks Bill A and Bill B (ascending id order), calls `completeReversalPosting()` once (swapping the original 2-line journal entry's debit/credit — unaffected by how many allocations exist), then loops `unsettleTarget()` over both rows: Bill A's `paidMinor -= 600`, Bill B's `paidMinor -= 400`. One `REVERSE` audit row on the payment, one `UPDATE` audit row per unwound bill — exactly the existing shape. **Result: the payment is reversed, both bills return to their pre-allocation `paidMinor`/`paymentStatus`, and no allocation row is deleted or modified** (they remain as a permanent historical record of what was, at the time, applied and then undone — consistent with every other reversal in this codebase never deleting history).

Definitive recommendation on the three options the CTO's instruction posed: **automatic full unwind of every currently-applied allocation**, exactly as the unchanged `reverse()` code already does. Rejecting reversal while allocations exist, or requiring explicit deallocation first, would both be regressions — they would make an on-account payment _harder_ to reverse than a fully-allocated one, contradicting the existing, uniform, all-document-types reversal contract this platform has already shipped (Document-Level Reversal). No new mechanism is introduced; the existing one is simply exercised with a larger `before.allocations` array than it has been exercised with before.

Transactional rollback: the entire sequence in `reverse()` — original-entry lock/validate, reversal-entry insert/post, every `unsettleTarget()` call, every audit row — remains inside the single `withTenant()` transaction it already runs in (§3.8). A failure at any point (e.g., a would-be-negative `paidMinor` from `unsettleTarget()`'s own invariant check) rolls back the entire reversal atomically; no partial unwind is possible today, and this proposal does not change that.

## 11. Reporting Impact

### 11.1 No change required (proven, not assumed)

Balance Sheet and Cash Flow Statement — §3.7. AP/AR ageing's bucket/outstanding calculation itself (`totalMinor - paidMinor`) — unchanged; it correctly continues to show a bill as outstanding until an allocation actually settles it, which is accounting-correct (§6.1) — an unmatched payment must not make a specific bill look paid.

### 11.2 Reconciliation — required change

`getApReconciliation()` (quoted from `ap-reports.service.ts:607-652`) currently computes:

```ts
differenceMinor =
  subLedgerTotalOutstandingMinor - glApControlAccountBalanceMinor;
reconciled = differenceMinor === 0;
```

Corrected formula:

```ts
differenceMinor =
  subLedgerTotalOutstandingMinor -
  unappliedPaymentsMinor -
  glApControlAccountBalanceMinor;
reconciled = differenceMinor === 0;
```

Reasoning: `glApControlAccountBalanceMinor` already reflects every posted payment's full cash amount, applied or not (§3.4/§6.1), net of any reversal already in effect as of the query's own cutoff (a reversed payment's swapped-polarity entry, once its own `transaction_date` is on or before the cutoff, cancels the original entry's contribution to this balance — existing, unmodified GL-query behavior). `subLedgerTotalOutstandingMinor` reflects only what remains owed _per bill_, which does not fall when cash is paid but not yet matched. Subtracting `unappliedPaymentsMinor` from the sub-ledger side removes exactly the amount that has already left the bank but not yet been matched to a specific bill **and is still in effect as of the same cutoff**, bringing both sides back to provable equality at every cutoff, not only "now." `ApReconciliationResult` gains one new field, `unappliedPaymentsMinor: number` (additive; no existing field removed or renamed — non-breaking). `ArReconciliationResult` gains the symmetric `unappliedReceiptsMinor`.

**Definitive definition of `unappliedPaymentsMinor` — one formula, no live/as-of split.** `getApReconciliation()`/`getSupplierBalance()` already branch between `asOfTotals()` (when `query.asOf` is supplied) and `currentTotals()` (when it is not, using `this.todayUtc()` as the effective cutoff for the GL-balance call either way — confirmed by direct re-read, `ap-reports.service.ts:607-652`/`159-203`). `unappliedPaymentsMinor` reuses this same `cutoffDate = query.asOf ?? todayUtc()` and is computed by **one** query, used identically whether or not the caller supplied `asOf` — there is no separate "live formula":

```sql
-- unappliedCashMinor(tx, tenantId, legalEntityId, supplierId | null, cutoffDate) — shared
-- helper, reused by getApReconciliation() and getSupplierBalance() (§23 risk mitigation),
-- byte-mirrored for AR with cra/cr/receipt_date/invoice_id.
SELECT COALESCE(SUM(sp.payment_amount_minor - COALESCE(applied.amt, 0)), 0) AS unapplied
FROM supplier_payments sp
LEFT JOIN journal_entries je ON je.id = sp.journal_entry_id
LEFT JOIN journal_entries rev_je ON rev_je.id = je.reversed_by_journal_entry_id
LEFT JOIN LATERAL (
  SELECT SUM(spa.allocated_amount_minor) AS amt
  FROM supplier_payment_allocations spa
  WHERE spa.payment_id = sp.id
    AND spa.allocation_date <= ${cutoffDate}::date
) applied ON true
WHERE sp.tenant_id = ${tenantId}
  AND sp.legal_entity_id = ${legalEntityId}
  AND sp.status = 'POSTED'
  AND sp.payment_date <= ${cutoffDate}::date
  AND (je.reversed_by_journal_entry_id IS NULL OR rev_je.transaction_date > ${cutoffDate}::date)
  ${supplierFilter}
```

This is the **exact same two-clause predicate** §11.4 defines for `asOfTotals()`'s own allocation subquery — `allocation_date <= cutoffDate` and "not reversed as of `cutoffDate`" — applied at the payment level instead of the per-bill level, plus one additional outer gate (`sp.payment_date <= cutoffDate`, the payment's own existence-as-of-cutoff test, needed here because this query is payment-driven and must also count a POSTED, not-yet-allocated payment; §11.4's own subquery does not need this gate independently because Rule 1 (§9.4) already guarantees `allocation_date >= payment_date`, so it is implied whenever an allocation row qualifies). Reusing one predicate for both the reconciliation term and `asOfTotals()` is not a coincidental convenience — it is _required_ for temporal consistency (§11.5): if `unappliedPaymentsMinor` and `asOfTotals()`'s bill-side reconstruction used two independently-written date/reversal conditions, a bug in either one could silently make reconciliation "balance" while telling a different historical story than the as-of report for the same date, which is precisely the failure mode a reconciliation report exists to catch, not produce.

**Why one formula covers both "live" and "as-of" call shapes.** Before this revision, "live" (`asOf` omitted) and "as-of-today" were only casually assumed equivalent. §9.4 Rule 2 (Option A) makes that equivalence a provable property, not an assumption: because `allocationDate` can never be later than `todayUtc()` (Rule 2) and the payment's own `paymentDate` can never be later than `todayUtc()` either (nothing in this codebase can post a document dated in the future — `resolveAndLockOpenPeriod()` is called with `todayUtc()`-bounded dates at every existing `post()` call site), every row that could ever match `cutoffDate = todayUtc()` is, definitionally, already in existence and already reflected in live state. There is no future-dated row waiting to "appear" in a live query that an as-of-today query would miss, and no historical row an as-of-today query would see that live state has not already applied. This is the direct payoff of choosing Option A over Option B (§9.4 Rule 2): it collapses what would otherwise be two formulas (and two chances for them to silently disagree) into one.

### 11.3 Balance visibility — required change

`SupplierBalanceResult`/`CustomerBalanceResult` each gain one new additive field, `unappliedPaymentsMinor`/`unappliedReceiptsMinor` (the identical `unappliedCashMinor(...)` helper from §11.2, scoped to one supplier/customer instead of the whole legal entity via the existing `supplierId`/`customerId` parameter, at `cutoffDate = query.asOf ?? todayUtc()` exactly as `getSupplierBalance()`/`getCustomerBalance()` already resolve their own effective date, confirmed by direct re-read at `ap-reports.service.ts:159-203`). `totalOutstandingMinor` itself is **not** changed — it continues to mean exactly what it means today (sum of open bill/invoice balances). This keeps the accounting-correct separation from §6.1/§11.1 explicit in the API surface rather than folding two different concepts into one number.

### 11.4 As-of correctness — the definitive reversal/as-of reconstruction rule

This section was revised after a complete, non-excerpted re-read of both `asOfTotals()` methods (AP: `ap-reports.service.ts:801-891`; AR: `ar-reports.service.ts:851-937`, every line confirmed, nothing skipped) specifically to resolve an apparent contradiction: `allocation_date` alone tells historical reporting _when_ an allocation happened, but not whether the parent payment was _later reversed_ — and without accounting for the latter, a report run after a reversal could still show a bill as settled by cash the ledger says was returned. The re-read confirms this is fully resolvable, using data that already exists, with no schema beyond the already-planned `allocation_date` column.

**The definitive rule:**

> For an as-of date `cutoffDate`, an allocation row contributes to a bill's/invoice's reconstructed `paidMinor` if and only if: **(a)** `allocation_date <= cutoffDate`, **and** **(b)** the allocation's parent payment/receipt's own journal entry had _not_ been reversed on or before `cutoffDate` — i.e. either it has never been reversed (`reversed_by_journal_entry_id IS NULL`), or it was reversed, but only _after_ `cutoffDate` (`the reversal entry's own transaction_date > cutoffDate`).

This is not a new mechanism. It is the identical two-part predicate the bill/invoice-side subquery of the _same_ `asOfTotals()` method already uses, in production, today — confirmed by full re-read at AP `ap-reports.service.ts:839-849` and AR `ar-reports.service.ts:886-895` — extended one FK hop further down a join path (allocation row → its parent payment/receipt → that parent's own `journal_entry_id`, a column already confirmed to exist at `supplier_payments.journalEntryId`/`customer_receipts.journalEntryId`) that the allocation subquery already partially traverses today (it already joins `spa → sp`/`cra → cr` for the supplier/customer-scoping filter). No third precedent needed to be invented; this is the third and fourth application of one pattern already proven twice in the same file.

**Exact SQL change (AP; AR is the byte-mirror with `cr`/`ci2`/`receipt_date`/`invoice_id` in place of `sp`/`b2`/`payment_date`/`bill_id`), before (current, lines 852-867) → after:**

```diff
         COALESCE((
           SELECT SUM(spa.allocated_amount_minor)
           FROM supplier_payment_allocations spa
           INNER JOIN supplier_payments sp ON sp.id = spa.payment_id
           INNER JOIN supplier_bills b2 ON b2.id = spa.bill_id
+          LEFT JOIN journal_entries je ON je.id = sp.journal_entry_id
+          LEFT JOIN journal_entries rev_je
+            ON rev_je.id = je.reversed_by_journal_entry_id
           WHERE spa.tenant_id = ${tenantId}
             AND sp.tenant_id = ${tenantId}
             AND sp.legal_entity_id = ${legalEntityId}
             AND sp.status = 'POSTED'
-            AND sp.payment_date ${cmp} ${cutoffDate}::date
+            AND spa.allocation_date ${cmp} ${cutoffDate}::date
+            AND (
+              je.reversed_by_journal_entry_id IS NULL
+              OR rev_je.transaction_date > ${cutoffDate}::date
+            )
             AND b2.tenant_id = ${tenantId}
             AND b2.legal_entity_id = ${legalEntityId}
             AND b2.status = 'POSTED'
             AND b2.bill_date ${cmp} ${cutoffDate}::date
             ${paymentSupplierFilter}
         ), 0)
```

`${cmp}` is the method's own existing `strict ? '<' : '<='` comparator, reused unchanged — the reversal-timing predicate's own `>` (strict, not parameterized by `cmp`) matches the bill-side subquery's identical predicate exactly, for the same reason: a reversal transacted _on_ `cutoffDate` itself is already in effect as of that date (the report is as of the _end_ of `cutoffDate`), so `> cutoffDate` (not `>= `) is what correctly excludes an allocation whose reversal has already landed by the report's own cutoff.

**Every required behavior, defined explicitly, with no ambiguity remaining:**

- **Allocation event timing:** the allocation row's own `allocation_date` column (§15), independent of its parent document's `paymentDate`/`receiptDate`.
- **Reversal timing:** the parent payment's/receipt's own journal entry's `reversed_by_journal_entry_id`, and — when set — the _reversal_ journal entry's own `transaction_date` (never the original entry's `transaction_date`, which does not change on reversal).
- **Later allocation timing:** each `applyAllocation()` call's rows carry their own `allocation_date`, independent of, and typically later than, both the parent's `paymentDate` and any earlier allocation event against the same payment.
- **Behavior before any allocation:** `appliedMinor(p) = 0` for every as-of date before the first allocation row's `allocation_date` — the allocation predicate's `(a)` clause excludes it, contributing nothing.
- **Behavior after allocation, before reversal:** the allocation contributes fully once `cutoffDate >= allocation_date`, provided clause `(b)` is satisfied (not yet reversed as of `cutoffDate`).
- **Behavior after reversal:** for any `cutoffDate >= ` the reversal's own `transaction_date`, clause `(b)` excludes every allocation of that payment/receipt, regardless of how far in the past each allocation's own `allocation_date` was — the bill/invoice reverts to its pre-allocation as-of state.
- **Repeated reversal prohibition:** a payment/receipt can be reversed at most once — enforced centrally, not by `asOfTotals()` itself, by `lockAndValidateOriginalForReversal()`'s `if (original.reversedByJournalEntryId !== null) throw new ConflictException(...)` (`journal-entries.service.ts:517-519`, confirmed by full re-read, race-safe under the row lock taken immediately before it). Because a document's journal entry can only ever carry one `reversed_by_journal_entry_id` value, `asOfTotals()`'s reconstruction never needs to reason about more than one reversal event per document.
- **Zero-allocation documents:** contribute `0` to `total_paid` at every `cutoffDate`, trivially — `SUM()` over zero matching rows, no special-case branch required anywhere in the query.

Worked through the CTO's own example, now fully resolved:

```
Day 1:  Payment posted, zero allocation.                    allocation rows: (none yet)
Day 10: Allocated in full, applyAllocation() called.         new row: allocation_date = Day 10
Day 20: Payment reversed.                                    reversal JE's own transaction_date = Day 20

Day 5  report (cutoffDate = Day 5):  clause (a) FALSE (Day 10 > Day 5) → excluded.
                                      → bill's as-of-Day-5 paidMinor = 0. ✓ (pre-allocation state)
Day 15 report (cutoffDate = Day 15): clause (a) TRUE (Day 10 <= Day 15); clause (b) TRUE
                                      (reversal transaction_date Day 20 > Day 15, not yet in effect)
                                      → allocation counted. → bill shown settled as of Day 15. ✓ (allocated state)
Day 25/Day 30 report (cutoffDate >= Day 20): clause (a) TRUE (Day 10 <= cutoffDate); clause (b) FALSE
                                      (reversal transaction_date Day 20 <= cutoffDate, already in effect)
                                      → allocation excluded. → bill shown outstanding again. ✓ (reversed state)
```

## 14. Transaction & Concurrency Model

### 14.1 What is locked, and when

`applyAllocation()` follows the exact lock-acquisition order every other mutating method in these two services already uses: **document header row first, target bill/invoice rows second, in ascending-`id` order.** This ordering — not merely "transactional" hand-waving — is what actually prevents deadlocks between two concurrent calls that touch an overlapping set of bills in a different order; it is the same reasoning `post()`/`reverse()` already rely on (§3.8), reused unmodified for the new method.

### 14.2 Concurrent scenarios, traced

- **Two concurrent `applyAllocation()` calls against the same payment.** Both take the header's `FOR UPDATE` lock; Postgres serializes them (the second blocks until the first's transaction commits or rolls back). The second call's Step 6 (`currentlyAppliedMinor` computation) then sees the first call's already-committed rows, so its own Step 8 inequality check is evaluated against up-to-date state. If the two calls' combined total would exceed the payment amount, the second fails with a clean `422`; if it would not, both succeed. This is the direct analogue of the existing `ap-payment-concurrency.e2e-spec.ts` scenario ("two concurrent payments together over-allocating one bill: exactly one 200, one 422"), applied to one payment's own remaining balance instead of one bill's.
- **`applyAllocation()` racing `reverse()` on the same payment.** Both take the header's `FOR UPDATE` lock first; they serialize. If `reverse()` wins: it commits, setting the journal entry's `reversedByJournalEntryId`; the queued `applyAllocation()` call then proceeds under its own now-acquired lock, re-reads the (now-reversed) `before`, and its Step 5 check throws `ConflictException` — a clean `409`, not a raw DB-trigger exception surfaced as a `500` (the trigger is defense-in-depth, per §9.3, not the primary rejection path). If `applyAllocation()` wins: it commits new allocation row(s) and bumped `paidMinor`; `reverse()` then proceeds under its own lock, re-reads `before` (now including the just-applied allocation(s)), and unwinds all of them correctly with zero code change (§10).
- **Two concurrent allocation attempts targeting the same bill from the same payment.** Both requests lock the payment header first (serializing at that point already), then the target bill under `FOR UPDATE`; Step 10's per-bill re-validation (`allocation.allocatedAmountMinor <= bill.totalMinor - bill.paidMinor`) is evaluated against the bill's live, post-first-call `paidMinor`, so an over-allocation of the _bill_ (as opposed to the payment) is rejected with the same `422` mechanism `post()` already uses today.
- **Two concurrent allocation attempts from _different_ payments, targeting an overlapping set of bills.** Unaffected by this proposal — this is exactly the scenario the existing `ap-payment-concurrency.e2e-spec.ts`/`ar-receipt-concurrency.e2e-spec.ts` suites already cover, and the fixed ascending-id bill-locking order this proposal reuses (not reinvents) is precisely what keeps it deadlock-free.

### 14.2a The concurrency invariant, stated explicitly (CTO Architecture Gate)

For every payment/receipt `p`: `SUM(allocatedAmountMinor over all of p's allocation rows) <= p.paymentAmountMinor` — this is Invariant 2 (§6.2), restated here as the specific property concurrency control must preserve. For every bill/invoice `b`: `b.paidMinor <= b.totalMinor` — Invariant 8 (§6.2), enforced additionally by the pre-existing DB `CHECK` constraint (`supplier_bills_paid_minor_within_total`/`customer_invoices_paid_minor_within_total`) as a second, independent layer beneath the application-layer lock-and-check sequence. Both invariants are preserved under concurrency specifically _because_ of, not merely alongside, the lock order in §14.1: Step 8's inequality check (§9.1) is evaluated only after the payment header's `FOR UPDATE` lock is held, so two concurrent `applyAllocation()` calls can never both observe the same stale `currentlyAppliedMinor` and both commit an over-total — the second call's Step 6 read is guaranteed to see the first call's already-committed rows, not a snapshot taken before them (§14.3). The same reasoning applies per-bill via Step 12's re-validation after the bill's own `FOR UPDATE` lock. This is not a new mechanism invented for this proposal — it is the exact mechanism `post()`'s own Step 8/Step 9 checks already rely on today, extended to the new call site. The quality gate proves this with an actual concurrent-request test (§19 Table 19.1, scenarios 42-43), not by code inspection alone, per the CTO's explicit requirement — two real HTTP requests issued concurrently against the same fixture row, asserting the database's final state directly (§19.2 item 1), not merely that one returned `200` and one returned `422`.

### 14.3 Isolation level

`READ COMMITTED` (the existing default, §3.8) is sufficient here, unchanged, because every value this proposal's logic depends on (`currentlyAppliedMinor`, each target bill's `paidMinor`) is read **after** acquiring the relevant `FOR UPDATE` lock, not before — so no other transaction can be mid-write on a value this method has already locked. No new isolation level, no new locking primitive, and no optimistic-concurrency/version column is introduced; none exists elsewhere in this schema to be reused (§3.8), and pessimistic locking is sufficient and consistent with the codebase's established pattern.

## 15. Schema Impact

**Schema change is required.** It is minimal, additive, and does not touch any existing table's shape beyond one constraint relaxation and one new column per allocation table.

### 15.1 `supplier_payment_allocations` / `customer_receipt_allocations`

```sql
-- New migration (next sequential number after 0021)
ALTER TABLE "supplier_payment_allocations" ADD COLUMN "allocation_date" date;
UPDATE "supplier_payment_allocations" spa
  SET allocation_date = sp.payment_date
  FROM "supplier_payments" sp WHERE sp.id = spa.payment_id;
ALTER TABLE "supplier_payment_allocations" ALTER COLUMN "allocation_date" SET NOT NULL;

ALTER TABLE "supplier_payment_allocations" DROP CONSTRAINT "supplier_payment_allocations_payment_bill_unique";
CREATE INDEX "supplier_payment_allocations_payment_bill_idx"
  ON "supplier_payment_allocations" ("payment_id", "bill_id");

-- Mirror for customer_receipt_allocations / customer_receipts (receipt_date, receipt_id, invoice_id)
```

Why a backfilled, `NOT NULL` date column rather than a nullable one: every pre-existing row was, in fact, created contemporaneously with its parent's own posting (today's only possible path), so `allocation_date = parent.payment_date`/`parent.receipt_date` is not a guess — it is the historically accurate value for every row that exists before this migration runs. This keeps `NOT NULL` provable rather than assumed, and keeps `asOfTotals()`'s rewritten predicate (§11.4) total, with no `NULL`-handling branch needed.

Why drop the unique constraint rather than keep it and merge via `INSERT ... ON CONFLICT DO UPDATE`: an `UPDATE` on an existing row would need its own `allocationDate`, and a single row cannot hold two different business dates for two different application events against the same bill — append-only rows, one per event, each with its own accurate `allocationDate`, is the only design that keeps §11.4's as-of reasoning exact. It is also consistent with the platform's broader convention of never mutating a financial record once it has accounting effect (immutability triggers everywhere else in this schema), extended here to allocation _events_ specifically rather than to the _document_ as a whole.

**No schema beyond `allocation_date` is needed to make as-of reporting reversal-aware (§11.4).** The reversal-timing half of §11.4's definitive rule reuses `journal_entries.reversedByJournalEntryId` and `journal_entries.transactionDate` — both already existing, already-populated columns, reached via `supplier_payments.journalEntryId`/`customer_receipts.journalEntryId`, both of which already exist today. This was confirmed by a complete re-read of the `journal_entries` schema and both allocation tables' current schemas (no other date/timestamp column exists on either allocation table today beyond `createdAt`) — the `allocation_date` column added by this migration is the only schema change §11.4 depends on.

### 15.2 Deliberately not added: a denormalized "applied so far" column on the header

`appliedMinor(p)` (§6.2) is always computed from `SUM(allocatedAmountMinor)` at read time, never cached on `supplier_payments`/`customer_receipts`. A cached column would need to be kept in lockstep with every `applyAllocation()` and every future write path that touches allocation rows, reintroducing exactly the kind of derived-state bug class the append-only design is meant to avoid, for a value that is cheap to compute (a single indexed `SUM` over a handful of rows per payment) and never needed at high volume/low latency (it appears only in report/detail responses, never in a hot posting path). No schema change here; recorded explicitly so a future reviewer does not read its absence as an oversight.

### 15.3 `008_...` / `012_...` trigger replacement — exact text (CTO Architecture Gate: written out in full, not left to implementation-time paraphrase)

New constraint file (next sequential number after the current highest in `drizzle/constraints/`), applied via `CREATE OR REPLACE FUNCTION` + `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER` against the same trigger name, idempotently, through the existing `apply-db-constraints.ts` runner — the same mechanism every other constraint file in this directory already uses; no change to that runner itself.

```sql
CREATE OR REPLACE FUNCTION prevent_posted_supplier_payment_allocation_mutation()
RETURNS TRIGGER AS $$
DECLARE
  target_payment_id uuid;
  parent_status supplier_payment_status;
  parent_journal_entry_id uuid;
  parent_reversed boolean;
BEGIN
  target_payment_id := COALESCE(NEW.payment_id, OLD.payment_id);

  -- UPDATE and DELETE remain unconditionally forbidden at every parent
  -- status, unchanged from the original trigger's own guarantee for
  -- those two operations (§3.5) — only INSERT's condition changes.
  IF TG_OP = 'UPDATE' OR TG_OP = 'DELETE' THEN
    RAISE EXCEPTION 'supplier_payment_allocations is immutable: % is never permitted on an existing row (payment_id=%)',
      TG_OP, target_payment_id;
  END IF;

  -- TG_OP = 'INSERT' beyond this point.
  SELECT status, journal_entry_id INTO parent_status, parent_journal_entry_id
    FROM supplier_payments WHERE id = target_payment_id;

  IF parent_status IS DISTINCT FROM 'POSTED' THEN
    RAISE EXCEPTION 'supplier_payment_allocations: a new allocation may only be inserted against a POSTED supplier_payment (payment_id=%, status=%)',
      target_payment_id, parent_status;
  END IF;

  SELECT (reversed_by_journal_entry_id IS NOT NULL) INTO parent_reversed
    FROM journal_entries WHERE id = parent_journal_entry_id;

  IF parent_reversed THEN
    RAISE EXCEPTION 'supplier_payment_allocations: a new allocation may not be inserted against a reversed supplier_payment (payment_id=%)',
      target_payment_id;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

Customer Receipts: byte-mirror with `receipt_id`/`customer_receipt_status`/`customer_receipts` in place of `payment_id`/`supplier_payment_status`/`supplier_payments`. Tenant/legal-entity isolation is deliberately **not** re-checked inside this trigger — it is enforced at the application/query layer (`validateAllocationsShapeOrThrow()`, §9.1 Step 7, and the tenant-scoped `findByIdInTx` lookup that resolves `target_payment_id`'s own row in the first place), consistent with every other trigger in this codebase, none of which independently re-derives tenant scoping (confirmed by re-reading the original 008/012 trigger text, §3.5, which does not either). §19.2 requires this exact trigger to be verified with raw SQL against a live PostgreSQL instance, not only through the HTTP layer (checks 1-5 below; checks 6-12 cover the surrounding schema/migration state).

## 16. Migration Strategy

One new Drizzle migration (`drizzle-kit generate` after the schema.ts edits below), one new constraints file per allocation table (superseding 008/012), applied via the existing `pnpm run migrate` (`drizzle-kit migrate && apply-rls.ts && apply-db-constraints.ts`) — no change to that script. Order of operations for a production rollout: (1) run the new migration (adds `allocation_date`, backfills it, drops the old unique constraint, adds the new non-unique index) — purely additive/backfilling, safe to run against a live table with no `payments`/`receipts` write-path change yet deployed; (2) deploy the new trigger version; (3) deploy the application code (Step 3/Step 9 relaxation + new endpoints) — this ordering means the database is never in a state where the new application code could be running against the old, stricter trigger or the old, NULL `allocation_date` column.

## 18. Failure/Rollback Model

Every write operation introduced by this proposal (`applyAllocation()`, in both modules) executes inside a single `withTenant()` transaction, identical in structure to every existing mutating method in these services (§3.8/§14.3). Failure-mode-by-failure-mode:

- **Validation fails** (Steps 3-8, 10): the relevant exception (`UnprocessableEntityException`/`ConflictException`/`NotFoundException`) is thrown before any `INSERT`/`UPDATE` statement runs; the transaction is rolled back in full by NestJS's/Drizzle's standard error-to-rollback path, identical to every existing guard in `post()`/`reverse()`. No partial state is ever written.
- **Allocation insert fails halfway** (e.g., a second bill in a multi-bill request violates a CHECK constraint the application-level Step 10 check somehow missed): the whole transaction rolls back — no allocation row from this call is left committed while another from the same call is not, because both are inside the same `tx`.
- **Audit insertion fails**: the audit `INSERT`s are the last statements in the transaction (Step 14), inside the same `tx` as every settlement `UPDATE` before them (identical placement to `post()`/`reverse()` today) — a failure here rolls back the settlement `UPDATE`s and the allocation `INSERT`s together, exactly as a failure in `post()`'s own final audit-insert step today would roll back that entire posting. This is not a new failure mode; it is the existing, already-relied-upon behavior of every mutating method in these two services.
- **Concurrent operation loses the race**: not a "failure" in the exceptional sense — it is a deterministic, correct outcome (§14.2) yielding either a normal `200` or a normal `422`/`409`, never a partial or corrupted state.
- **Reversal fails** (e.g., the period is closed): `resolveOpenPeriodOrThrow()` throws before any write in `reverse()` — unaffected by this proposal, since `reverse()` itself is unmodified.
- **Report query encounters partial state**: impossible by construction — every report reads only committed data (via `REPORT_TX_CONFIG`'s `REPEATABLE READ, READ ONLY` transaction, §3.8), and every write this proposal introduces is atomic per the points above, so there is no window in which a report could observe an allocation row without its corresponding bill settlement, or vice versa.

**Atomicity is demonstrated, not asserted**: every state change this proposal introduces (new allocation row(s), target bill `paidMinor`/`paymentStatus`, audit rows) is written inside one transaction opened at the top of `applyAllocation()` and never committed until every step has succeeded — the same pattern independently verified for `post()` and `reverse()` in this investigation (§3.2, §3.6) and reused without modification here.

### 19.2 Non-scenario-numbered gate requirements (not part of the 50)

1. **Real accounting-value assertions, never HTTP-status-only.** For every scenario above that has a non-`—` "Expected Accounting/Allocation/Reporting/Audit-RBAC Result," the test asserts the actual persisted/derived value, not merely the HTTP status code — via a direct Drizzle `withTenant()` select against the DB (bypassing the HTTP response body), the same pattern `supplier-payments.e2e-spec.ts:888-923` already uses. Concretely, wherever applicable: the payment's/receipt's own header `amountMinor`; every new allocation row's `allocatedAmountMinor` and `allocation_date`; the cumulative allocation total; the resulting `unappliedMinor`/`unappliedPaymentsMinor`; the target bill's/invoice's exact `paidMinor` and `paymentStatus`; the journal entry's own id and `reversed_by_journal_entry_id` linkage (unaffected/affected as expected); the exact `journal_lines` debit/credit amounts; the exact `audit_logs` row(s) (`action`, `entityType`, `entityId`, before/after state, `actorUserId`); the `reconciled`/`differenceMinor` result; the as-of reconstruction result; and tenant/legal-entity isolation (a query scoped to tenant A never returns tenant B's rows). A `200`/`422`/`409` status code alone never counts as a passing assertion for any scenario in Table 19.1 that has a non-`—` result column.
2. **Independent raw-SQL cross-check** for scenarios 36-37 and 47-49 (§11.2/§11.3/§11.5): a scratch/local helper query computing `unappliedPaymentsMinor`/`unappliedReceiptsMinor` independently of `getApReconciliation()`'s/`getSupplierBalance()`'s own implementation, asserted equal to the service's own returned value — mirroring the `rawCashTotal()`-style independent cross-check convention established in the Cash Flow Statement work item's own e2e suite.
3. **Raw PostgreSQL trigger and schema verification (CTO Architecture Gate) — verified directly against the database, never inferred from an HTTP response alone.** All twelve of the following are executed as direct `psql`/raw-SQL statements (or an equivalent Drizzle raw-`execute()` call) against a real PostgreSQL instance running the post-migration schema, independent of and in addition to the HTTP-level scenarios above:
   1. `INSERT` into the allocation table against a `POSTED`, not-reversed parent → succeeds (the one new operation §15.3's replacement trigger permits).
   2. `INSERT` against a `DRAFT` parent → raises the trigger's own exception, transaction rolled back.
   3. `INSERT` against a `POSTED`-but-reversed parent (`reversed_by_journal_entry_id IS NOT NULL` on the parent's journal entry) → raises, rolled back.
   4. `UPDATE` of any column on an existing allocation row, at any parent status → raises, rolled back.
   5. `DELETE` of an existing allocation row, at any parent status → raises, rolled back.
   6. An allocation `INSERT` whose `payment_id`/`bill_id` cross a tenant or legal-entity boundary is rejected at the **application/query layer** (`validateAllocationsShapeOrThrow()`, RLS-scoped `withTenant()`), not by this trigger (§15.3 explicitly does not re-derive tenant scoping) — verified by attempting the equivalent raw `INSERT` under a session lacking the matching RLS grant and confirming Postgres' own RLS policy (not this trigger) is what blocks it.
   7. Two allocation `INSERT`s for the identical `(payment_id, bill_id)` pair (duplicate allocation event, distinct rows, distinct `allocation_date`s) → both succeed, confirming the unique constraint was genuinely dropped and replaced by a non-unique index, not merely relaxed in application code while the DB constraint still silently blocks it.
   8. Post-migration: `SELECT COUNT(*) FROM supplier_payment_allocations WHERE allocation_date IS NULL` → `0`.
   9. Pre-migration snapshot vs. post-migration: `SELECT COUNT(*) FROM supplier_payment_allocations` is identical before and after — the migration adds a column and backfills it; it drops zero rows.
   10. `SELECT conname FROM pg_constraint WHERE conname = 'supplier_payment_allocations_payment_bill_unique'` → no row (constraint genuinely dropped, not merely unused).
   11. `SELECT indexname FROM pg_indexes WHERE indexname = 'supplier_payment_allocations_payment_bill_idx'` → one row (replacement index genuinely present).
   12. `SELECT tgname FROM pg_trigger WHERE tgrelid = 'supplier_payment_allocations'::regclass AND NOT tgisinternal` → the replacement trigger (§15.3) is present and is the only allocation-mutation trigger on the table (the superseded 008 trigger's function/trigger no longer exists under its old semantics).

   All twelve are byte-mirrored for `customer_receipt_allocations`/`012_...`. None of these twelve is satisfied by an HTTP `200`/`4xx` response alone, per the CTO's explicit instruction.

4. **Full regression**: the entire existing unit (`npx jest`, last known baseline 618/618, 65 suites) and e2e (`npx jest --config jest-e2e.config.js`, last known baseline 989/989, 47 suites) suites must continue to pass unmodified in every test not covered by scenarios 1-50, directly proving scenario 45's regression claim rather than by inspection alone.
5. **Migration safety — strengthened acceptance criteria (CTO Architecture Gate).** Before the migration is declared successful, all of the following are verified, not merely the backfill's existence:
   1. `npx drizzle-kit migrate` runs clean against a fresh (empty) database.
   2. `npx drizzle-kit migrate` runs clean against a database seeded with the full existing fixture set (pre-existing allocation rows present).
   3. Every pre-existing allocation row's `allocation_date` equals its parent's `payment_date`/`receipt_date` after migration (§15.1's backfill claim, verified against a snapshot of the pre-migration fixture data, not merely asserted in prose).
   4. `allocation_date` backfill row count equals the pre-migration allocation row count exactly (raw-SQL check 9 above).
   5. Zero `NULL` values in `allocation_date` before the `NOT NULL` constraint is applied (raw-SQL check 8 above) — the migration is written so the backfill `UPDATE` and the `SET NOT NULL` are two separate, ordered statements in the same migration file, never combined into one statement that could silently succeed against an incompletely-backfilled table.
   6. No existing allocation row is lost, duplicated, or reordered by the migration (row count and primary-key set identical before/after).
   7. The old `unique(payment_id, bill_id)` constraint is confirmed absent post-migration (raw-SQL check 10).
   8. The replacement non-unique index is confirmed present post-migration (raw-SQL check 11).
   9. The replacement trigger (§15.3) is confirmed present and behaves per all twelve raw-SQL checks above (item 3), run again specifically in the post-migration environment, not only in a hand-built test schema.
   10. The migration is additive-only against the existing production data shape — no table dropped, no column removed, no existing column's type changed (confirmed directly from the migration SQL itself, §15.1) — and is safe to run against a live table with no concurrent write-path change yet deployed (§16's ordering guarantee), verified by running the migration against a copy of the fixture data while a separate, unrelated write-path test suite runs concurrently, confirming no lock contention beyond an ordinary `ALTER TABLE`'s brief exclusive lock.

## 20. Security / Isolation

Tenant/legal-entity scoping is unchanged: every query this proposal introduces filters on `tenantId`/`legalEntityId` using the same `withTenant()` RLS-scoped transaction and the same explicit `WHERE` clauses every existing method already uses (`validateAllocationsShapeOrThrow`, `findByIdInTx`, the bill-locking query). No new cross-tenant or cross-legal-entity surface is introduced. RBAC is unchanged in shape (§13) — no new role, no widening of an existing role's reach. No new PII or sensitive field is introduced; `allocationDate` is a plain business date, not a secret.

---

## 21. Performance Considerations

`applyAllocation()`'s additional cost over the existing `post()` is one `SUM()` query (Step 6, `currentlyAppliedMinor`) over a small, indexed set of rows (the new `supplier_payment_allocations_payment_bill_idx` index on `(payment_id, bill_id)` from §15.1 makes this a fast index-range scan, not a table scan). `asOfTotals()`'s rewritten predicate (§11.4) trades one date-column comparison (`sp.payment_date <= cutoffDate`) for another (`spa.allocation_date <= cutoffDate`) — no additional join, no measurable cost change. `getApReconciliation()`/`getArReconciliation()`'s new `unappliedPaymentsMinor` term is one additional aggregate query per call, scoped and indexed identically to the existing `currentTotals()`/`asOfTotals()` queries it sits beside. No N+1 query pattern is introduced anywhere in this design — every multi-row operation (bill locking, allocation insertion, audit-row insertion) is a single batched statement, matching the existing convention in `post()`/`reverse()`.

---

## 22. Observability

No new logging/metrics infrastructure exists anywhere in this codebase to extend (confirmed — no structured logger, no metrics emitter found in either module during investigation); this proposal introduces none, consistent with that baseline. The audit log (§12) is the system's existing mechanism for after-the-fact observability of exactly what allocation events occurred, by whom, and with what before/after state — no gap exists here that a new mechanism would need to fill.

## 24. Explicit Decisions

**Decision A — GL presentation of unapplied cash.** No new GL account, account type, or settings field. The existing header-amount-driven journal posting already represents the accounting correctly (§6.1). The genuine gap is in the _reconciliation report_, not the GL: `getApReconciliation()`/`getArReconciliation()` gain an explicit `unappliedPaymentsMinor`/`unappliedReceiptsMinor` reconciling term (§11.2), and `getSupplierBalance()`/`getCustomerBalance()` gain a visible, separate `unappliedPaymentsMinor`/`unappliedReceiptsMinor` field (§11.3) — additive, non-breaking, and kept explicitly distinct from `totalOutstandingMinor` so the accounting-correct separation (unmatched cash vs. per-bill outstanding) is legible in the API, not just in the ledger. Recommended because it requires no new schema concept, changes no existing behavior, and is directly provable from the existing chart-of-accounts architecture (§6.1) rather than introduced by assumption.

**Decision B — Reversal after later allocation.** Automatic full unwind of every currently-applied allocation, using the existing, unmodified `reverse()`/`unsettleTarget()` machinery (§10) — zero new mechanism. A reversed document is permanently barred from receiving any further allocation (§9.3, enforced at both the application layer and the DB trigger layer). Recommended because it is the only option requiring zero new code in the highest-risk path (reversal) and the only option consistent with this platform's existing, uniform, all-document-types reversal contract.

**Decision C — Audit action semantics.** Reuse `UPDATE` for every allocation-application event (§12); no new audit action string. Recommended because the existing `action` column is free-form and already uses `UPDATE` for exactly this class of event (a mutation to an entity's persisted state) elsewhere in the same two services, and introducing a thirteenth distinct free-form string for a case the existing vocabulary already covers would be inconsistent with the codebase's own established convention rather than required by any gap in it.

**Decision D — Ageing presentation.** Ageing's own calculation (`totalMinor - paidMinor`) does not change — an unmatched payment must not make a specific bill's ageing bucket look settled, which would misstate what is actually overdue (§6.1/§11.1). Visibility of on-account cash is added as a separate, explicit field on the balance endpoints (§11.3), not folded into the ageing bucket or the outstanding total. Recommended because it is the only option that does not conflate two accounting-distinct concepts (per-bill settlement state vs. aggregate unmatched cash) into one number.

**Decision E (new, surfaced by this investigation, not in the original four) — `allocationDate` schema addition.** A new, backfilled, `NOT NULL` `allocation_date` column on both allocation tables, populated from the parent document's own business date for every pre-existing/contemporaneous row and independently supplied (or defaulted to today) for every later `applyAllocation()`-created row (§11.4/§15.1). Recommended because it is the only option that keeps as-of/historical reporting deterministically correct once allocation and posting can happen on different dates — without it, §11.4's Day-5/Day-15/Day-25 worked example cannot be satisfied by any query, no matter how it is written, because the information needed (when a specific allocation event actually happened) would not exist in the data model at all.

**Decision F (new) — append-only allocation rows, unique constraint relaxed rather than merge-on-conflict.** One new row per allocation event, `unique(paymentId, billId)` replaced with a plain index (§15.1). Recommended because it is the only option compatible with Decision E (a single mutable row cannot hold two different business dates for two different events) and because it extends, rather than breaks, this codebase's existing convention of never mutating a financial record once it carries accounting effect.

**Decision G (new, CTO Architecture Gate Blocker 1 resolution) — reversal-aware as-of reconstruction.** `asOfTotals()`'s allocation-side subquery is extended with the same `LEFT JOIN journal_entries je / LEFT JOIN journal_entries rev_je ON rev_je.id = je.reversed_by_journal_entry_id` pattern already proven in production on the bill/invoice-side subquery two lines above it, joined via the allocation's parent payment/receipt's own `journal_entry_id` (§11.4). The definitive rule: an allocation row contributes to an as-of reconstruction iff `allocation_date <= cutoffDate` AND the parent's journal entry either was never reversed, or was reversed only after `cutoffDate`. No new schema is required beyond the already-planned `allocation_date` column (Decision E) — the join reuses `journal_entries` columns that already exist and are already populated for every payment/receipt. Recommended because it is a mechanical, one-FK-hop extension of an existing, already-correct, already-tested pattern rather than a new reporting mechanism, minimizing both design risk and implementation surface.

**Decision H (CTO Architecture Gate Blocker 2 resolution; Rule 2 superseded by Decision I below) — allocation-date / accounting-period semantics.** Seven definitive rules (§9.4) govern `allocationDate`: (1) may not precede the parent document's own posting date, newly invented and enforced at the application layer only, since no existing cross-document date-comparison precedent exists anywhere in the codebase; (2) may not be later than `todayUtc()` — see Decision I; (3)-(4) period validity (open/closed/no-covering-period) reuses the existing `resolvePeriodForDate()`/`resolveAndLockOpenPeriod()` machinery verbatim; (5) an omitted `allocationDate` defaults to `todayUtc()`, mirroring `reverse()`'s own established default pattern; (6) validation is always against the allocation event's own period, never the parent document's, again mirroring `reverse()`'s precedent of never re-validating the original posting's period; (7) period-open enforcement applies to `applyAllocation()` even though it creates no `journal_entries` row — a genuine first fork with no precedent either way, resolved by enforcing, reasoning from the convention's stated purpose (gating financially significant state changes) rather than its narrow mechanical co-location with journal-entry creation in all 15 existing call sites. Recommended because six of the seven rules reuse conventions already proven correct elsewhere in this codebase, and the two genuinely new rules (1 and 7) are each justified independently from the absence of contrary precedent rather than by default or convenience.

**Decision I (new, CTO Final Architecture Gate — future-dated allocation, Option A selected) — `allocationDate` is capped at `todayUtc()`; a future-effective allocation is rejected outright, superseding this proposal's earlier draft position (§9.4 Rule 2).** The CTO's gate offered two options: (A) cap at today, or (B) formally define ten distinct future-effective semantics questions. Direct repository evidence resolves the choice: this codebase's only established mechanism for a genuinely future-effective financial event, `scheduled_reversals` (`schema.ts:2795-2830`), is a deferred-execution design — a `SCHEDULED` status with zero live effect until a background claiming job (`WHERE status = 'SCHEDULED' AND target_date <= cutoff`) reaches its `targetDate` and only then invokes the ordinary posting path. `applyAllocation()` has no such mechanism, and building one (a second scheduling/claiming/execution subsystem, parallel to `scheduled_reversals`) would be a substantial, unapproved scope expansion into infrastructure this work item was never scoped to touch — the overdesign the CTO's own gate instruction separately warns against. Recommended because it is the only option consistent with both the CTO's explicit fallback instruction and this codebase's own established precedent for what "future-effective" actually requires here. Direct, provable consequence: because no allocation or posting date can ever exceed `todayUtc()`, live state and as-of-today state are now identical at all times (§11.5), eliminating an entire class of live/as-of divergence outright rather than reasoning around it case by case.

**Decision J (new, CTO Final Architecture Gate — temporal consistency) — `unappliedPaymentsMinor` (§11.2/§11.3) is computed by exactly one formula, shared with `asOfTotals()`'s own reversal-aware predicate, for both the "live" and "as-of" call shapes.** No separate live formula is introduced. `getApReconciliation()`/`getSupplierBalance()` already resolve an effective cutoff date (`query.asOf ?? todayUtc()`) before delegating to `asOfTotals()`/`currentTotals()` (confirmed by direct re-read); `unappliedPaymentsMinor` reuses that same cutoff and the identical `allocation_date <= cutoffDate` / "not reversed as of `cutoffDate`" predicate (§11.2's `unappliedCashMinor()` helper). Recommended because it is what Decision I (above) makes possible — with future dates foreclosed, one formula is provably sufficient — and because sharing one predicate across `asOfTotals()`, reconciliation, and balance visibility is what makes it structurally impossible, not merely untested, for these three report surfaces to disagree about the same document at the same cutoff (§11.5). This directly strengthens, rather than replaces, the risk-table mitigation already recorded in §23 requiring one shared helper.
